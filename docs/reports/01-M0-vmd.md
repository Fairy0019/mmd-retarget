# 阶段报告 01 · M0-① VMD 读写

- 日期：2026-10-23
- 范围：`src/mmd_retarget/vmd.py`、`tests/test_vmd.py`、`tools/bench_vmd.py`、`inspect` 子命令
- 结论：**达到 M0-① 验收标准**，可以对真实 2.9 MB / 140 骨 / 5640 帧动作做
  **字节级无损** round-trip。

---

## 1. 做了什么

| 能力 | 实现 |
|---|---|
| 文件头 | 30 字节，兼容前 25 字节为 `Vocaloid Motion Data 0002` 的文件；保留原始头 |
| 模型名 | 20 字节 CP932，NUL / `0xFD` 填充均可解码 |
| 骨骼帧 | 111 字节定长，位置 `3f`、四元数 `4f`（xyzw）、64 字节插值原样保存 |
| morph 帧 | 23 字节定长 |
| 相机 / 灯光 / 自阴影 / IK | 以原始记录保存，数量与记录一致时写回完全一致 |
| 未知尾部 | 存入 `Vmd.trailer`，写回原样追加 |
| 插值 | 解码 4 通道贝塞尔控制点；`sample_curve()` 提供 x→y 采样 |
| 容错 | `strict=False` 时把无法解释的尾部当作 trailer，不丢字节 |
| CLI | `inspect file.vmd [--json]` 输出模型、帧范围、骨骼/morph 统计 |

设计上刻意**不**把相机/灯光解码成结构化对象：M0 不需要，而且保留原始字节
才能保证任何第三方文件都能无损写回。

## 2. 验收结果

### 2.1 真实文件

样本：`mmd-vision/assets/motion/恋爱循环.vmd`（私有素材，不入库）

```
size       2,937,042 bytes
model      初音ミク
bones      140 unique / 25,973 keyframes
morphs      31 unique /  2,344 keyframes
frames      0 – 5639 (187.967 s @ 30fps)
```

| 指标 | 结果 |
|---|---|
| 解析耗时 | **0.086 s** |
| 写出耗时 | 0.043 s |
| round-trip | **字节完全一致**（2,937,042 / 2,937,042） |
| 四元数归一化 | 25,973 帧全部 ‖q‖−1 < 0.01 |
| 骨名 | 140 个日文名全部正确，无乱码 |

### 2.2 合成压力测试

`tools/bench_vmd.py`，140 骨 × 5640 帧 = **789,600** 条关键帧，87.6 MB：

| 阶段 | 耗时 |
|---|---|
| 生成测试数据 | 155 ms |
| 解析 | **3.40 s**（232,281 帧/s） |
| 写出 | 1.22 s |
| round-trip | 字节完全一致 |

验收线是 5640×140 在 10 秒内，当前余量约 2.9×。

### 2.3 单元测试

`pytest -q`：**24 passed**。覆盖：

- 空文件 / 单帧 / 多帧；
- 日文骨名、morph 名；
- 超长骨名按**字符边界**截断（不会切出半个双字节字符）；
- CP932 无法编码的字符（emoji）降级为 `?`；
- 相机 / 灯光 / 自阴影 / IK 记录保留；
- 未知尾部保留；
- 截断文件报错并带 offset；
- 插值编解码、线性曲线恒等、贝塞尔单调；
- `0xFD` 填充的第三方文件字节级往返；
- “count=0 但后面仍有一条相机记录”的异常文件可 salvage。

## 3. 漏洞与风险思考

按影响排序。**这些不是待办清单，而是后续阶段必须记住的约束。**

### 3.1 关键帧不保证有序（已确认）

真实文件里 `左腕` 的帧号顺序是 `…3638, 3435, 3471, 3644…`。VMD 只要求
帧号唯一，不要求文件内有序。任何“顺序扫描 + 线性插值”的实现都会算错。

**约束**：`canonical` 阶段必须先按帧号排序、处理重复帧，再做重采样。
本轮解析器**故意不改顺序**，保证 round-trip；排序责任放在语义层。

### 3.2 插值 64 字节的“不可靠区”

只有前 16 字节是权威控制点，后 48 字节是历史冗余。不同导出器（MMD 本体、
MMD Tools、VmdSizing）填的值并不一致，MMD 本身也不读。我们的策略是：

- 读入：原样保存 64 字节；
- 新建：前 16 字节按列优先写控制点，其余按对角线补零；
- 解码：只读前 16 字节。

**风险**：如果将来需要“修改曲线后写回”，后 48 字节会与真实 MMD 输出不同。
语义上无害，但无法与原始文件逐字节对比。需要在 M1 做曲线编辑时补一个
“MMD 本体输出样本”回归。

### 3.3 count 与实际记录不一致的文件真实存在

样本文件在 morph 段之后是：`camera_count = 0`，但紧跟着一条**完全合法**的
61 字节相机记录，再之后 `light_count = 0`。这导致按标准顺序解析时，
自阴影数量被读成 49676，越界。

处理方式：`strict=True` 报错并给出 offset；`strict=False` 把从 camera 段
开始的 69 字节整体存为 trailer，写回原样。**代价是这条相机记录不会出现在
`camera` 列表里**。对 M0（只关心骨骼）无影响，但 M2 若要做机位相关的可见性
判定，必须单独实现“相机段启发式恢复”，不能假设 count 可信。

### 3.4 帧率是隐含约定

VMD 没有 fps 字段，业界默认 30。若源动作按 60fps 制作后抽帧，帧号语义会变。
`canonical` 需要在元数据里显式写 `fps: 30`，并且**不允许**在重定向时改帧率，
否则脚锁的“每帧最大位移”阈值会失真。

### 3.5 骨名编码的边界

- CP932 与严格 Shift-JIS 在 0x5C（¥）等字符上行为不同；统一用 CP932；
- 15 字节限制按**字节**而非字符，7 个全角字符就用掉 14 字节；
- 0xFD 在 CP932 里是半角片假名，不是合法的名称结尾，解析时 rstrip；
- 同名骨骼的重复关键帧不去重，交给语义层。

### 3.6 性能与内存

789,600 条 `BoneFrame` 是 789,600 个 Python 对象。3.4 s 达标，但内存峰值
约数百 MB。若 M1 要在 Blender 里逐帧求解，应改为 **numpy 结构化数组**
（列式存储），否则 GC 压力会拖慢 IK。当前 API 先保证可读性，后续可在
`canonical` 层换存储，不影响调用方。

### 3.7 解析器的攻击面

VMD 是不可信输入。当前所有 `count × record_size` 都先做边界检查再分配，
不会因为 `count = 2^32-1` 直接 OOM；但 `list` 预分配没有上限保护，
一个 88 MB 文件可以合法地产生数百万对象。若未来做 Web 服务，需要加
“最大帧数 / 最大文件尺寸”配额。
