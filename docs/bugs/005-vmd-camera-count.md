# 005 · VMD 相机段 count=0 但后面仍有一条合法记录

| 项 | 内容 |
|---|---|
| 日期 / 状态 / 严重度 | 2026-10-23 · 已修（salvage） · **中** |
| 发现方式 | 真实文件解析越界（自阴影数读成 49676） |
| 相关报告 | `docs/reports/01-M0-vmd.md` §3.3 |

## 现象

按标准顺序解析：morph 段之后 `camera_count = 0`，但紧跟着一条**完全合法**
的 61 字节相机记录，再之后才是 `light_count = 0`。于是“自阴影数量”被读成
49676，越界。

## 根因

文件生成器在写相机段时把 count 写成了 0，却仍然输出了记录。
标准解析假设 `count == 记录数`，这个假设被打破。

## 修复

- `strict=True`：报错并给出 offset，便于定位；
- `strict=False`：从 camera 段开始把 69 字节整体存为 `trailer`，写回**原样保留**，
  并打印 warning；
- 代价：这条相机记录不会出现在 `camera` 列表里。

## 为什么这么修

- M0 只关心骨骼；为了不丢数据，最稳的是“原样存尾部”，而不是猜着解析；
- 一旦开始猜（启发式恢复），就要处理更多异常组合，风险大于收益；
- 写回保留 trailer，保证 round-trip 不破坏源文件。

## 波及面排查（重点）

| 位置 | 影响 |
|---|---|
| M0 骨骼解析 | 无（已越过的段） |
| **M2 可见性 / 机位** | **有影响**：依赖 `camera` 列表的功能会拿不到相机 |
| 写回 | trailer 原样保留，字节级一致 |
| 其他工具链 | 任何“重新序列化 VMD”的工具都可能丢这条记录 |

**同类排查清单**：

- [ ] 所有带 count 的段，解析后是否校验 `offset` 与文件长度一致？
- [ ] 不一致时是“报错”还是“猜”？猜的代价是否评估过？
- [ ] trailer / 未知段是否原样保留？
- [ ] 依赖相机段的功能（可见性、机位）是否明确标注了“count 不可信”？

## 回归测试

`tests/test_vmd.py` 覆盖“count=0 但仍有记录”的样本：
`strict=False` 可 salvage，`strict=True` 报错并给出 offset。

## 教训

- **真实文件比规范更野**：count 字段不可全信，解析器要能“安全地失败”；
- 能原样保留就不要重写，尤其是自己当前用不到的段；
- 把一个已知限制写进文档（“相机段需要单独恢复”），比假装支持更安全。
